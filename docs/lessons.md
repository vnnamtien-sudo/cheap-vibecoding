# 我们做错了什么（11/16 复盘）

[← 返回 README](../README.md) | [English](lessons.en.md)

开源之后，我们拿 GitHub 上的同类项目、官方省钱说明和多路并行的公开经验，回头核对了自己的做法。结论：**方向没错，主攻方向偏了**。每一步确实便宜了 39%，可每份交付反而贵了 19%。钱的大头不在“读文件”，在下面三处。

## 一、每个会话开工前读的东西太厚

- 主会话一开张就有约 11 万 token 的固定内容（系统说明、工具说明、我们自己的规矩和记忆），**之后每走一步都要整份重读一遍**。按估算价目，这块固定内容约占每一步花费的三分之一。
- 其中我们自己写的规矩和记忆，瘦身前约 4 万字：根目录规矩约 1.6 万字，全局规矩约 0.5 万字，记忆索引约 1.9 万字。为了省钱加的规矩，本身成了固定开销。
- **改了什么**：根目录规矩压到 1.35 万字；记忆索引只留常用的 125 条（约 0.6 万字），其余 164 条挪到另一份文件，用到时再查。合计少了约 1.5 万字。
- **更正**：我们第一次估的时候把字节数当成了字数，以为规矩有 3 万字，以为瘦身能省掉每步约六分之一。按字数重算，这次瘦身实际省下的大约是每一步的 5% 左右。

## 二、同时开的路太多

- 一台 64 GB、24 线程的电脑上，我们同时跑了约 20 路会话。公开经验大多认为，一台 32 GB 的机器实际能跑 5–6 路，普通笔记本 4–5 路。
- 后果：测试排长队（卡 10 分钟以上的测试，67% 是在等位子）；机器被挤卡；为了管住拥挤，又加了排队、熔断、让路等规矩，越管越复杂。真正的瓶颈其实是“验收看不过来”。
- **改了什么**：同时干活的会话降到最多 8 路，试一周，11/24 复量。

## 三、考核看错了数

- 我们一直拿“每一步多少钱”当成绩。这是零件指标。按交付算，每份交付贵了 19%，每美元写出的程序少了 21%。
- 人工逐条读了约 208 条验收结论，真打回 71 次，**约三次打回一次**，多数是没拿真实数据和旧系统对、没跑测试。返工的钱比读文件省下的多。
- **改了什么**：考核只看三个数：每项通过验收的功能花多少钱、从派单到上线几天、验收打回率。写代码前先拿真实数据对旧，测试跑过才交验收，打回率目标降到五次以内一次。
- **还没做好**：我们新写的查数程序是粗口径，自动统计的打回率只有 5–8%，和人工逐条读的约 34% 差很多，口径还在校准。

## 四、有些轮子不用自己造

- 用量统计已有成熟的开源工具（例如 [ccusage](https://github.com/ccusage/ccusage)、[splitrail](https://github.com/Piebald-AI/splitrail)），同时支持多家。我们自己的查数脚本只为了按阶段对比，日常看用量直接用现成的就行。
- 读文件限行钩子在社区里也有好几个同类做法（[cc-safe-setup](https://yurukusa.github.io/cc-safe-setup/token-saving-hooks.html)、[read-once](https://dev.to/boucle2026/read-once-a-claude-code-hook-that-stops-redundant-file-reads-4bjk)）。这说明方向对，但谈不上独创。

## 什么时候补结果

- 11/24：复量降到 8 路之后，每项功能的花费、上线天数、打回率，和降之前比。
